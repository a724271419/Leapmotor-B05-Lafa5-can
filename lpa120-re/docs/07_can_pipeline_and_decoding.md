## 3. CRP1 协议（实时流）

来源：`G:\deepseek\can to debian\can-remote-system\can-remote-analyzer\Protocol\Crp.cs`

```
帧头 24B: magic "CRP1" | ver=1 | type | flags | 0 | crc32(hdr[0..8]) | bodyLen(u32) | corrId(u64)
帧体    : body
帧尾 4B : crc32(body)

MsgType: Hello=1 HelloAck=2 FrameBatch=3 DurableAck=4 Subscribe=5 SubscribeAck=6
         LiveBatch=7 GapNotice=8 Ping=9 Pong=10 Error=11 ResumeRequest=12 ...

LiveBatch body:
  40B 头: sessionId(uuid16) | first(u64) | last(u64) | count(u32) | flags(u32)
  每条记录 36B: seq(u64) | canId(u32) | channel(u8) | flags(u8) | dlc(u8) | len(u8)
                | quality(u8) | capture(u8) | pad(2) | tsMono(u64) | tsUnix(u64) | payload

flags 位: Extended=0x01 Fd=0x02 Brs=0x04 Esi=0x08 Remote=0x10
```

订阅请求体：`{"device_ids":[], "id_ranges":[]}`（空数组 = 全部）

**客户端只需**：连 WS → 发 Subscribe → 收 LiveBatch → 每 10 s 发 Ping。

实现见 `G:\Codex\ota_probe\can_live.js`（约 200 行，零依赖，Node 24 内置 WebSocket）。

## 更正 · 纵向(ACC)与横向(LCC)必须分开统计（2026-11-02）

**此前表述**："LCC 激活占比 23%" —— 只统计了横向，漏掉纵向，容易被误解为"巡航"。

**实车验证的功能层级**（用户确认 + 数据证实）：

```
ACC 是基础功能；LCC 是 ACC 之上的子功能（有车道线才叠加）
→ 只有两种组合：仅 ACC、ACC+LCC
→ "仅 LCC" 结构上不可能
→ 车道线丢失时 LCC 退出，ACC 保持
```

### 数据验证（`cap_c3286193`，16,522 帧 0x18D）

```
横向 lat=1        : 4,078 帧 (24.7%)
纵向 acc=1        : 7,064 帧 (42.8%)
lat=1 且 acc=0    : 0 帧        ← 不变式成立
LCC 退出事件 4 次，ACC 全部保持   ← 与描述一致
```

### 正确判据

| 维度 | 信号 | 判定 |
|---|---|---|
| 纵向 ACC | `0x0B7 byte3` bit6=ACCStates / bit4=ACCRequest | `0x40` 已介入、`0x10` 请求中 |
| 横向 LCC | `0x18D byte8` bit3 | 仅在 ACC 已激活时可能为 1 |
| LKA 命令枚举 | `0x083 byte12[2:0]` | `LKA.FuncMode = byte12 & 0x07`，实测值 `{1,2,3,5}`；完整字节中的 `0x0B/0x4B` 含其它位，禁止再按 `0xB` 判断 |
| 命令回显 | `0x142 byte5[2:0]` | 逐帧回显上述 `LKA.FuncMode`，不是独立状态证据；实际横向执行只认 `0x18D byte8.bit3` |

### 对 openpilot 的影响

```
cruiseState.enabled 必须看 ACC（纵向）
只读 latActive 会把 "ACC 开着但车道居中未激活" 的 31 秒误判为未开辅助
```

解码器 `decode_capture.js` 已补 `accActive` / `accRequest` 两列，并内置不变式检查（输出 0 为正常）。

**采集端时间基只有 1 ms**，不是导出精度，也不是重复入队。完整证据链见 `08_timebase_data_quality.md` §1：

```
PCAN µs 硬件时戳 → 被 XOR 进 captureFlags → 丢弃
手机 App        → timestampUnixUs = System.currentTimeMillis()*1000  (硬 1 ms)
录制文件         → 只存 timestampUnixUs
服务端导入       → timestamp_monotonic_ns := int(ts)*1000  (合成)
```

反证：200 fps 的诊断总线会话 `878e8239` 重复率为 **0.0%**；1200 fps 的 CCAN 会话为 44.7–55.7%（2 帧/ms）。

## 14. 转向灯极性确认（2026-11-04）

数据：`can抓包\左转向10秒右转向10秒双闪10秒.trc`（PCAN-View 导出，76,134 帧 / 68.2 s / 39 ID）

| 时间段 | b3.0 | b3.1 | 动作 |
|---|---|---|---|
| 8–18 s | 活跃 | — | 左转向 |
| 28–38 s | — | 活跃 | 右转向 |
| 48–58 s | 活跃 | 活跃（计数相等） | 双闪 |

**结论（零歧义）**

```
0x290 byte3 bit0 = 左转向灯
0x290 byte3 bit1 = 右转向灯
双闪 = 两位同时为 1
单侧打灯时另一位严格为 0
```

CarState 写法（**状态取 b2，b3 只做极性校验**）：

```
isLeft   = (b[2] & 0xE0) == 0x20
isRight  = (b[2] & 0xE0) == 0x40
isHazard = (b[2] & 0xE0) == 0x80
leftBlinker  = isLeft  || isHazard
rightBlinker = isRight || isHazard

// 极性自检（可选，用于发现错帧/换件）
assert isLeft  implies (b[3] & 0x02) == 0
```

⚠️ **不要直接用 b3 当状态**：同批 76,134 帧里，左转期间 `b3.0=1` 仅 117 帧、`b3.0=0` 有 108 帧（右转 106/89、双闪 89/90）——b3 是 1.25 Hz 的灯输出，直接当 `leftBlinker` 会让信号每秒翻转一次。b3 的价值是**极性**：左只亮 bit0、右只亮 bit1、双闪两位同 1，单侧时对侧严格为 0。

**至此 CarState 9 个核心字段全部闭环，无待定项。**
