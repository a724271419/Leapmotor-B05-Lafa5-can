# 08 · 时间基准与数据质量（2026-11-03）

> 本文回答 `07_can_pipeline_and_decoding.md` §12.3 的第 1 条待办：
> **"定位重复时间戳成因（导出精度 vs 采集端）→ 决定哪些旧结论需重算"**。
> 结论已经用**代码 + 数据**双侧证据闭合，并顺带更正了 2.9 g 的错误归因。

## 0. 三句话结论

1. **现有数据有两条时间路径**：`fullcap` 的旧 Android/中继归档只有 1 ms 分辨率；
   `can抓包` 的 11-03 PCAN 直采字段是 µs 表示，但**帧间隔仍是 1 ms 栅格**（见 §2.1 的 Δ 直方图）。
   `dq_gate.js` 按 **Δ 分布**识别有效栅格，不按“值是否落整毫秒”判——后者会把小数漂移误认成可用的 µs 帧序。
   两类数据都可能有大量同戳帧，跨 ID 对齐仍用 `sequence`，dt 量仍用 ≥100 ms 窗口。
2. **0x182（整车车速）是突发门控发送**：内部 counter 按 20 ms 持续推进，外层主要以约 1.3–1.4 s
   周期开窗；43%–82% 的时间里整段不在总线上。**vEgo 应改用 0x184（50 Hz、在线率 100%、
   与 0x182 中位差 −0.16 km/h）**。
3. 旧文档把"峰值减速度 28.48 m/s²"归因于时间戳重复是**错的**：真因是 **0x182 采样陈旧 + 60–80 ms 短窗口**。
   改用轮速源 + ≥200 ms 窗口后，干净会话给出 **3.66 / 3.83 m/s²**。

## 1. 证据链：旧 Android/中继路径中 µs 时戳在哪一层被丢掉

| 层 | 位置 | 事实 |
|---|---|---|
| 采集器（PCAN-USB FD） | `PcanProtocol.kt` `PcanEvent.timestampLow/High` | uCAN 硬件时戳，**µs 精度**，可用 |
| 手机 App 入队 | `RealCanUsbAdapter.kt:270-278` | `timestampMonotonicNs = System.nanoTime()`（真 ns）；`timestampUnixUs = System.currentTimeMillis() * 1000L`（**硬 1 ms**）；`captureFlags = (tsLow xor (tsHigh shl 16))` ← **硬件 µs 时戳被异或成垃圾塞进一个随后被丢弃的字段** |
| 本地录制 | `RecordWriter.kt:79` | 每帧 24 B 头只写 `timestampUnixUs`；`timestampMonotonicNs` **不进盘** |
| 服务端导入 | `can-relay-server/can_relay/records.py:44` | `timestamp_monotonic_ns = int(ts) * 1000` ← **由 ms 合成** |
| 归档 API | `/history` 实测 | `ns = 1793633815020000000` / `us = 1793633815020000`（恰为 ×1000） |
| 本地 ndjson | 本文 §2 实测 | 75% 的行 ns 带 ±64/±128 ns 抖动 → 这是**导出侧 float64 往返**（JS 大整数精度）留下的指纹，不是设备精度 |

**旧路径净结果**：一条 µs 时间戳，从采集器到分析脚本，精度逐层降到 **1 ms**，且"ns"字段是 ms 的复写。

**11-03 PCAN 直采是另一条路径**：字段保留三位 ms 小数，但大量帧同戳，正帧间隔中
**98.55% 落在整毫秒 ±2 µs**、99.87% 落在 ±3 µs（`运动跨0`）。因此它只能提供约 1 ms 的
**有效帧间排序栅格**，不能用于亚毫秒差分。小数漂移究竟来自接收批次时钟、PCAN 时间换算，
还是 ECU 调度时钟偏差，现有文件无法区分。

## 2. 量化实测（14 条旧中继会话）

### 2.0 数据源与 candump 解析纪律

- 旧会话分析权威源使用 `fullcap\*.ndjson`；11-03 直采使用 `can抓包\*.ndjson`，TRC 只作对质。跨 ID 对齐统一使用 `sequence`，不得按 `timestamp_unix_us` 等值 join。
- CAN-FD candump 格式为 `ID##<2位flags><payload>`。例如 `18D##107802...` 中 `10` 是 BRS/ESI flags，真实 payload 从 `78` 开始；把 flags 当 payload 或只剥 1 个十六进制字符会造成固定半字节错位。
- 服务器与 GUI 导出器都直接拼接 flags 和原始 `DataHex`，无 payload 重排。已出现的 `27 37 d0` 是 `42 73 7d 00` 被错误切分后的结果，**不是导出损坏**。
- candump 仅用于人眼检查；如必须解析，应先与同一 `sequence` 的 ndjson 做逐字节对质。
- **独立复核（2026-11-03）**：对 `c3286193` 全量比对（服务器 `/export?format=candump` vs ndjson，按 sequence 顺序）——
  `198,619` 帧、**ID 失配 0、payload 失配 0**；会话内 sequence 有 70 处空洞（共缺 98 个号），
  说明导出完整、无重排。脚本：`ota_probe\parity_check.js` `parity_tail.js`。

| 指标 | 值 |
|---|---|
| `timestamp_unix_us % 1000 == 0` | **14/14 会话 = 100%** |
| 重复时间戳占比（12 条 CCAN 会话） | **44.7% – 55.7%** |
| 每毫秒帧数 | **2.02 – 2.04** |
| 878e8239（诊断总线，200 fps，1 帧/ms） | **重复 0.0%** ← 反证：重复完全由"每毫秒 ≥2 帧"决定 |
| sequence 单调 | 14/14 无逆序 |

> 判定式：`dup ≈ 1 − P(本毫秒内只有 1 帧)`。2 帧/ms 时约 50%，与实测吻合。
> **因此"重复时间戳"不是异常，是 1 ms 时间基在 1200 fps 下的正常表现。**

### 2.1 第二个数据源：PCAN-View `.trc`（2026-11-03 起）

场景包 `can抓包\*.trc` 由 PCAN-View v5.3.3 直接录制，格式 `FILEVERSION=2.0, COLUMNS=N,O,T,I,d,l,D`。
转换器：`ota_probe\trc2ndjson.js`（输出字段与 `fullcap\*.ndjson` 完全一致，现有工具零改动可用）。

**结论（2026-11-03 二次定案）：字段有 µs 表示位数，但有效帧间排序仍由约 1 ms 栅格主导。**

判据不能只看"值是否落整毫秒"；应检查**帧间隔分布、同戳比例及逆序点**：

```
运动跨0（47,769 帧）帧间隔统计：
  0 µs        23,805  (49.8%)
  999 µs       5,563
  1,000 µs     9,614
  1,999 / 2,000 / 2,999 / 3,999 / 4,998 / 5,998 / 6,997 …
  100 µs           2   ← 全文件仅 2 次，不是分辨率证据
  900 µs           4
=> 正 Δ 中 98.55% 落在整毫秒 ±2 µs，99.87% 落在 ±3 µs；另有 49.8% 相邻帧同戳
```

因此：

1. **有效帧间排序量子约为 1 ms**，`timestamp_unix_us` 的小数位不能用于 CAN 帧亚毫秒先后；
   但没有外部基准时钟，不能把观察到的漂移直接定性为“整段时间快 0.1%”，也不应施加 0.1% 校正。
2. `dq_gate.js` 的判据已改为**按 Δ 分布**（正 Δ 在整毫秒 **±10 µs < 99%** 且同戳 ≤ 1% → `microsecond-candidate`；否则 1 ms 栅格），
   不再用 `% 1000` 判；也**不再只看 ±2 µs**——第二批 5 个包 ±2 µs 只有 89.6–94.8% 曾被误判成旧标签 `microsecond`，2026-11-03 已修（标签同时改名为 `microsecond-candidate`）。
   实测：17 个场景包 **17/17** 判 1 ms 栅格。该判据表示“这份数据不可提供可靠亚毫秒帧序”，
   不是对底层硬件时钟物理分辨率的通用证明。
3. 分析纪律与手机源相同：dt 类量窗口 ≥100 ms，跨 ID 对齐用 `sequence`。
4. 6 个场景文件：39 个 ID、1095–1144 fps、42–91 s，与手机侧 CCAN 画像一致。
5. 6 组 TRC 重新运行 `trc2ndjson.js` 后与现有 ndjson 的 SHA-256 **逐文件完全相同**（523,903 帧，skipped=0）——可复现性成立。
6. `运动跨0` 有 3 次 `timestamp` 回退 100 µs，而 `sequence` 仍单调；`dq_gate.js` 会单独 WARN，跨 ID 排序继续只认 sequence。

## 3. 逐 ID 在线率（本轮新发现）

以 100 ms 窗口统计"该 ID 至少出现一次"的比例（`69229f22`，234 s）：

| 类别 | ID | 在线率 |
|---|---|---|
| 满勤 | 0x18D 0x186 0x0FD 0x083 0x0B7 0x184 | 100% |
| 接近满勤 | 0x0B1 0x0B6 0x0CB 0x0CD 0x18C | 97%–100%（偶发 0.4–0.9 s 长间隔） |
| **条件发送** | **0x182 29.7%** / 0x227 60% / 0x185 62% / 0x142 63% / 0x243 64% / 0x0FA 68% / 0x143 69% / 0x233 84% | 显著低 |

**0x182 缺口形态（决定性证据）**：

```
gap 1720 ms: 同期有 0x18D 172 帧、0x184 83 帧，其它 ID 共 255 帧
gap 1480 ms: 0x18D 148 帧、0x184 73 帧
（共 184 段 >300 ms 静默，合计 173.9 s / 233 s）
```

→ 若是采集丢帧，同一 FIFO 里的 0x18D 必然同时缺；
实际 0x18D 满勤，**说明那段时间总线上确实没有 0x182**（条件发送 / 网关按需转发）。
0x182 的滚动计数跨静默仍与间隔严格成 20 ms/步，说明内部时基持续推进，而不是静默时停表。

**11-03 场景包补充（排除“仅运动门控”）**：

| 场景 | 0x182 帧数 / 平均率 | 中位间隔 | p90 | 最大间隔 | >300 ms 静默 |
|---|---:|---:|---:|---:|---:|
| 先下单拨、再下双拨（全程静止） | 493 / 5.64 Hz | 40 ms | 740 ms | 2,579 ms | 68 段 |
| 左/右/双闪（全程静止） | 342 / 5.01 Hz | 20 ms | 980 ms | 3,959 ms | 46 段 |
| 低速行驶 | 522 / 5.94 Hz | 40 ms | 660 ms | 1,639 ms | 70 段 |
| 去 | 573 / 6.27 Hz | 20 ms | 360 ms | 2,839 ms | 64 段 |
| 回 | 478 / 5.35 Hz | 40 ms | 1,020 ms | 2,819 ms | 59 段 |
| 运动跨0 | 183 / 4.32 Hz | 20 ms | 1,120 ms | 4,019 ms | 27 段 |

结论：0x182 平时以 20–40 ms 间隔成簇发送，簇间有 0.3–4.0 s 静默（这只是下表 6 个包的上界；30 文件全量 max 46.38 s）；静止时同样发送。
N5 对 30 个文件的进一步复验得到：counter/20 ms 步进 15,705/15,705，速度变化 AUC p50=0.500，
簇首间隔 p50=1.301 s 且 73.9% 在 1.2–1.6 s。因此不是运动/变化率门控，而是约 1.3–1.4 s
的外层突发窗；精确开窗条件位于源 ECU、网关或调度队列，当前 CCAN 不能区分。

**双源一致性**（好会话）：0x182 与四轮均值中位差 **−0.16 km/h**，p95 ≤ 0.08 km/h；
`287ce0ae` 例外（最大差 3.67 km/h，见 §5）。

**跨会话稳定性**：对 `fullcap` 目录下全部 14 条会话跑 `dq_gate.js`，"条件发送"名单高度一致 ——
`0x182 / 0x227 / 0x185 / 0x142 / 0x143 / 0x0FA / 0x243 / 0x2A3 / 0x233 / 0x241 / 0x290`
在 13 条 CCAN 会话里反复出现，说明是**车型固定的发送策略**，不是偶发丢帧。

> 注意：`7c5c1486`（26 ID、279 fps 的早期片段）会把 `0x186/0x0FD/0x184` 等也标成"低在线"，
> 因为该会话的参考帧 0x18D 本身就稀疏（相机/域控未完全上电）。这类会话不参与在线率结论。

## 4. 影响面：哪些结论要重算，哪些不受影响

| 结论 | 状态 | 处理 |
|---|---|---|
| 任何"相邻帧时间差"派生的量（减速度、加速度、周期） | ❌ 需重算 | 窗口 ≥ 100 ms；**推荐 200 ms** |
| 峰值减速度 28.48 m/s² | ❌ 作废 | 真因更正见 §5 |
| "0x0B6 周期 11.3–11.6 ms / 0x0B1 10.5–12.5 / 0x0CB 10.4–14.1" | ❌ **撤销** | 14/14 会话**中位数恒为 10.0 ms**；旧值是"均值"，被缺帧拉高（见下表） |
| "0x182 周期 20 ms" | 🟡 部分成立 | 突发内为 20 ms；整体 6–8 fps，在线窗口 29.7% |
| vEgo 取自 0x182 | ⚠ 改为 0x184 | 0x184 = 50 Hz、在线 100%、与 0x182 一致 |
| 值域 / 位布局 / 档位编码 / 刹车饱和 100 / 转角公式 / CRC | ✅ 不受影响 | 均为**逐帧值**，与时间无关 |

周期对照（14 会话全部一致）：

| ID | 中位周期 | 均值（旧文档口径） |
|---|---|---|
| 0x0B6 | **10.0 ms** | 11.2–11.6 ms |
| 0x0B1 | **10.0 ms** | 10.3–12.5 ms |
| 0x0CB | **10.0 ms** | 10.0–14.1 ms |

> **教训**：`(last−first)/(n−1)` 是"含缺帧的平均周期"，不是总线周期；总线周期必须用**中位数**。

## 5. 更正：28.48 m/s² 的真因不是时间戳重复

原结论（`04_failures_gotchas.md` G5 / `06` §9.6）：时间戳重复导致 dt 失真。

**实际复现**（`287ce0ae`，原算法：0x182 + 200 ms 滑窗）：

```
t=−41ms 33.23 | −20ms 31.71 | 0ms 29.99 | +79ms 21.89 | +120ms 23.02 | +140ms 24.41  (km/h)
```

- 该窗口内 0x182 只有 2 帧，间隔 79 ms，**样本陈旧**；
- 同刻四轮速与 0x182 最大差 3.67 km/h；
- 8 km/h 的落差落在 79 ms 上 → 28.48 m/s²。

**时间戳重复不是主因**：0x182 自身 20 ms 周期的相邻帧几乎不会撞同一毫秒，dt 一直是 79–100 ms 级别。

改用 **四轮速 + 200 ms 窗口 + 剔除窗口内 >60 ms 空档**：

| 会话 | 峰值减速度 |
|---|---|
| `69229f22` | **3.66 m/s²** |
| `c3286193` | **3.83 m/s²** |
| `287ce0ae` | 18.45 m/s²（仍异常） |

`287ce0ae` 的 18.45 已定位到**单轮瞬变**：前左轮 60 ms 内 32.00 → 26.50 km/h 后回升到 30.38，
同期后轴 32.2 → 22.4。属 ABS/滑移或单轮传感器瞬变，**不能当整车减速度**。
→ 建议：整车减速度用四轮**中位数**（或先做 3 点中值滤波），并单独标注单轮异常。

## 7. 工具

### 7.1 `G:\Codex\ota_probe\dq_gate.js` —— 数据准入闸门

```powershell
node G:\Codex\ota_probe\dq_gate.js <cap.ndjson> [more.ndjson ...] [--json]
```

输出：帧率、时间戳分辨率、重复率、帧/ms、sequence 单调性、逐 ID 中位周期/在线率/最长间隔、
条件发送 ID 名单，以及**该数据允许做哪些分析**的判定行。

判定规则：
- 时间基判定（2026-11-03 修订）：正 Δ 在整毫秒 **±10 µs < 99%** 且同戳 ≤ 1% → `microsecond-candidate`；否则 `millisecond-grid`。两者都可通过，只影响「能否做亚毫秒排序」
- 名字是 **candidate**：Δ 分布只证明数据含亚毫秒信息，不证明物理时钟精度（合成用例：均匀 µs → candidate、严格 1 ms 周期 → grid、µs 但 50% 同戳 → grid）
- **只看 ±2 µs 会误判**：第二批 5 个包 ±2 µs 仅 89.6–94.8%，但 ±10 µs 达 99.83–99.92%、同戳 44–56% —— 那是 1 ms 栅格上的抖动，不是可用的 µs 时间基
- timestamp 或 sequence 逆序 → FAIL
- 重复率 > 1% → WARN（dt 类量必须 ≥100 ms 窗口）
- 某"快"ID（中位 ≤100 ms）在线率 < 90% 且显著低于 0x18D → WARN（条件发送/丢帧）
- 自检夹具：`G:\Codex\ota_probe\dq_gate_selftest\`（3 个合成包 + README）。期望：均匀 µs → `microsecond-candidate`、严格 1 ms 周期 → `millisecond-grid`、µs 但 50% 同戳 → `millisecond-grid`。**改判定前后各跑一次**
