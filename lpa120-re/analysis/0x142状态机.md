# 0x142 LKA.FuncMode 命令回显（原“状态机”线，只读重建）· 2026-11-03

## 结论

`0x142` 是 16B、条件发送的 ADAS 帧。其 `byte5[2:0]` 已确认不是独立状态机，而是
`0x083 byte12[2:0]`（`LKA.FuncMode` 命令）的原样回显。跨 `fullcap` 中 11 条含该帧的会话，共 26,727 帧：

- byte5 低 3 位只出现 `1 / 2 / 3 / 5`，构成稳定四值命令枚举；
- 命令回显值 `3` 与 `0x18D byte8.bit3`（已验证的 `latActive` 执行反馈）高度一致；
- byte7.bit2 在全量样本中严格满足 `b7.2 == (state != 1)`，0 次违反；
- byte6.bit6、byte8.bit5 是低占空比状态位，但与 LCC 边沿没有稳定近邻关系，暂不命名。

## 证据边界

### 观察

| 项 | 全量结果 |
|---|---:|
| 0x142 帧数 | 26,727 |
| FuncMode 回显=1 | 11,998 |
| FuncMode 回显=2 | 5,849 |
| FuncMode 回显=3 | 8,046 |
| FuncMode 回显=5 | 834 |
| 其它值 | 0 |
| `b7.2 != (state != 1)` | **0** |

以命令回显值 `3` 预测 0x18D `latActive`：

| TN | FP | FN | TP | 准确率 |
|---:|---:|---:|---:|---:|
| 18,674 | 11 | 7 | 8,035 | **99.93%** |

18 个差异集中在不同周期帧的切换边沿，符合命令先变、执行反馈后跟，以及 0x142 条件发送与 0x18D 10 ms 周期错开的预期。

### 推断（尚未由原厂位布局或 UI 场景逐项命名）

| FuncMode 回显值 | 数据侧特征 | 候选解释 | 置信度 |
|---:|---|---|---|
| 1 | b7.2=0；latActive=0 | 不可用/关闭 | 中 |
| 2 | b7.2=1；latActive=0 | 可用/待机 | 中高 |
| 3 | b7.2=1；latActive≈1 | LCC 在控 | 高 |
| 5 | b7.2=1；latActive=0；单段可持续约 2–6 s | 非在控的另一工作态（可能暂停/抑制/接管相关） | 低 |

配置中确有“LCC工作状态”“是否允许驾驶员开启LCC功能”“LCC接管请求”等 0x142 信号名，但 signalId 顺序不是位序，因此不能仅凭名称把 state=5 定义为接管或故障。

## 字段身份（2026-11-03 追加）：b5[2:0] 就是 0x083 的 LKA.FuncMode

**这是本轮最重要的修正**：`0x142` 的 `byte5 & 0x07` 不是一个独立状态机，而是
**`0x083` 命令帧 `byte12 & 0x07`（LKA.FuncMode）的原样回显**。

验证方法（`ota_probe\m142_lag.js`，11 条会话，sequence 对齐）：

| 对齐方式 | 样本 | 一致 | 不一致 |
|---|---:|---:|---:|
| 最近邻（±50 seq） | 26,726 | 26,726 | **0（100.00%）** |
| **严格：取该 0x142 之前最近的一条 0x083** | 26,727 | 26,726 | **1**（间隔 ≤100 seq 的切换边沿） |

交叉表（严格配对）：

```
0x142 state / 0x083 FuncMode   1/1    2/2    3/3    5/5
帧数                          11998   5849   8045    834
```

**推论（会改变接入方式）**：

1. 0x142 `state` 证明的是 **HPC 下发了 FuncMode 几**，**不是** EPS/FSC 在执行什么；
   它与 0x083 同源，**不能当独立第二证据**。
2. **执行证据仍只有 0x18D `byte8.bit3`**（EPS 反馈）。“FuncMode 回显=3 作命令→执行一致性检查”的结论保留，
   但理由要改写：它校验的是**命令通路**，不是**执行通路**。
3. 这也解释了主表的 18 个边沿差异（FP 11 / FN 7）：命令位先变、EPS 反馈后跟，
   20 ms 与 10 ms 两个周期在切换瞬间天然错开，不是异常。
4. `FuncMode = 5` 是**命令侧真实存在的枚举值**，语义仍未知，维持"不映射为故障/接管"。

## 命令枚举转移

实测主路径包括：

```text
1 ↔ 2
2 → 3
3 → 2 / 1
3 ↔ 5
5 → 1 / 2
```

`10`（b5.1=1、b7.2=0）在全量样本中从未出现；`01` 对应 FuncMode=5 等命令值。此前只看 b5.1/b7.2 两个位会把值 2 与 3 合并，因此必须按 byte5 低 3 位解码。

## 补充取证：四态上下文（2026-11-03，独立复核）

用 `ota_probe\m142_state4.js`（4 态解码 + sequence 对齐）在 11 条会话上独立复算，
**与主表逐项一致**（26,727 帧；state 1/2/3/5 = 11,998/5,849/8,046/834；b7.2 违反 0；
TN/FP/FN/TP = 18,674/11/7/8,035，99.93%）。在此基础上补做了每个状态与 ACC/LCC 的联合统计：

| state | 帧数 | ACC 已介入 | LCC 在控 | 连续段时长 p50 / max |
|---:|---:|---:|---:|---|
| 1 | 11,998 | 34.3% | 0.0% | 2.92 s / 42.4 s |
| 2 | 5,849 | **3.8%** | 0.0% | 2.00 s / 15.4 s |
| 3 | 8,046 | **100.0%** | 99.9% | 10.28 s / 72.7 s |
| 5 | 834 | **100.0%** | 0.6% | 2.32 s / 7.02 s |

由此得到两条命令上下文判据（把值 5 从“语义未知”提升到“有数据支撑”；不把它当 EPS 执行状态）：

1. **FuncMode 2 vs 5 的上下文差别不是 LCC，而是 ACC**：
   `2` 有 96.2% 的时间 ACC 未介入，`5` 则 100% 处于 ACC 已介入、LCC 未在控。
   → 候选语义可细化为：`2 = 可用但未开 ACC（待机）`、`5 = ACC 已开、LCC 待命/未接管`。
2. **FuncMode 回显 3 ⇒ ACC 已介入（100%）**：可作为命令/上下文断言（若出现回显值 3 且 ACC=0，属异常样本，应打标而不是静默接受）。

`decode_capture2.js` 已实现该断言，只在 0x142 FuncMode 回显与 0x0B7 ACC 均未超过 `--max-age` 时计数。`69229f22` 的 50 Hz 回归为 **0 / 3,758** 个可判定栅格违反。

> 与主表一致，FuncMode=5 仍**不映射**为接管/故障/steerFaultTemporary：
> 其段内 |方向盘扭矩| 中位数仅 0.14 Nm（无驾驶员持续施力特征），且 ACC 全程在控。

11-03 新包 `can抓包\去` 又出现一段 3.00 s 的 FuncMode=5（50 Hz 共 151 行）：
ACC=1 为 151/151、latAvail=1 为 151/151、latActive=1 仅 1/151（切换边沿），
车速 47.93–48.28 km/h，|方向盘扭矩| 中位 0.072 Nm。它强化了“ACC 在、横向未执行且仍可用”的边界，
但文件没有该瞬间的人工标签，仍不能在“待命/退出过渡/抑制”三者中唯一命名。

### 可复现性说明

主表（四态）由 `ota_probe\m142_state4.js` 复现；`m142_state.js` 只做 `b5.1/b7.2` 两位置的信道审计
（占用率、按 lat/acc 分层、边沿匹配），不含 3 位状态解码，**不能复现主表**。

## openpilot 接入规则

```python
lka_func_mode_083 = data083[12] & 0x07
lka_func_mode_echo_142 = data142[5] & 0x07
lka_available_echo_142 = bool((data142[7] >> 2) & 1)  # 冗余回显；等价于 mode != 1（本数据集）
lka_command_mode3_echo_142 = lka_func_mode_echo_142 == 3  # 命令侧诊断，不是执行反馈
```

安全使用边界：

1. `CarState.cruiseState.enabled` 继续取 `0x0B7` 的 ACC 状态，不能取 0x142；
2. 横向实际在控的主判据继续取 `0x18D byte8.bit3`；0x083/0x142 的值 3 只用于命令→执行一致性检查/降级诊断；
3. 0x142 是条件发送帧，陈旧时不得保持为真；必须带 age/超时；
4. FuncMode=5 不得直接映射为故障、接管或 temporaryFault，等待有标签场景验证；
5. 本表是只读重建，不用于构造或发送 CAN 帧。
